# harness-guide

> **Отвечает за:** краткий рассказ о харнесе для человека и агента: состав, порядок работы, выбор скилла, границы автономии, с чего начать.
> **Не содержит:** самих правил и фактов, они живут в файлах-владельцах по ссылкам: возможности ([capabilities.md](../../../docs/harness/capabilities.md)), команды и флаги ([reference.md](../../../docs/harness/reference.md)), устройство ([infrastructure.md](../../../docs/harness/infrastructure.md)), гейты ([quality-gates.md](../../../docs/harness/quality-gates.md)), кирпичики и уровни контроля ([bricks.md](../../../docs/harness/bricks.md)).
> **Читать когда:** пользователь вызвал `/harness-guide`, впервые открыл репозиторий или спрашивает, как здесь устроена работа с агентами.
> **Проверено при версии конституции:** 3.0.0

**TL;DR:** харнес ведет фичу от идеи до задач (Spec Kit), исполняет задачи по ролям (OMC) и держит правила и документацию согласованными (обвязки проекта). Ниже карта состава, порядок работы и таблица "какой скилл когда". Счетчики и состояние берутся командами, а не из этого файла.

## Шаги

1. Пойми, что нужно пользователю: общий обзор, с чего начать, какой скилл подходит его ситуации, что произойдет само, где потребуется его решение.
2. Возьми живое состояние командами, не из памяти: `python3 tools/stage.py list` показывает этап и число коммитов после него, `python3 tools/work.py board` показывает эпики и прогресс, `python3 tools/work.py next` показывает, что можно брать, `ls .claude/skills` показывает скиллы проекта и Spec Kit.
3. Ответь коротко по разделам ниже, выбирая только нужные. На каждый факт давай ссылку на файл-владелец, не пересказывай его целиком.
4. Если вопрос упирается в тему из [реестра отложенных решений](../../../docs/decisions/README.md#отложенные-решения), скажи, что тема не решена, и не придумывай содержимое.

## Что такое харнес

В репозитории два проекта: сервис совместного просмотра фильмов и харнес, то есть среда, которая делает работу ИИ-агентов над сервисом предсказуемой. Границы зон описаны в [docs/harness](../../../docs/harness/README.md#две-зоны-репозитория). Харнес собран из трех источников:

- Spec Kit ведет жизненный цикл фичи: спецификация, план, задачи, реализация.
- OMC исполняет утвержденные задачи агентами по ролям: исследование, тесты, реализация, проверка. Планирование по фиче ему запрещено, планирует Spec Kit.
- Обвязки проекта держат правила, знания и документацию согласованными: инструкции, скрипты, хуки, скиллы, тесты.

## Как строится работа

1. Цель попадает в трекер: `/epic-new` раскладывает ее на фичи вместе с владельцем. Простые элементы (задача, баг, исследование) заводит `/work`, он же отвечает на вопросы "что дальше" и "как идет работа".
2. Архитектурный вопрос решается через `/decide`: варианты, рекомендация, выбор владельца, ADR, тема уходит из реестра отложенных решений.
3. Фича берется в работу через `/work-start`: он проверяет готовность и зависимости и передает описание в `/speckit-specify`. Открытые вопросы закрывает `/speckit-clarify`. Спецификацию утверждает владелец.
4. Перед `/speckit-plan` хук Spec Kit вызывает `/hot-zones` и спрашивает владельца о горячих зонах. План проходит Constitution Check. Затем `/speckit-tasks` раскладывает план на задачи с тестами первыми, `/speckit-analyze` сверяет спецификацию, план и задачи.
5. Реализация идет через `/speckit-implement` по порядку из [AGENTS.md](../../../AGENTS.md#выполнение-задачи): исследование в research.md, тест падает по правильной причине, минимальная реализация, проверка по конституции и [code-review.md](../../../code-review.md). Роли OMC по шагам заданы в [CLAUDE.md](../../../CLAUDE.md#omc). После реализации хук Spec Kit запускает `/docs-sync`.
6. Шаги без диалога можно прогнать цепочкой `feature-chain`: план, задачи, реализация, синхронизация документов, после каждого шага проверка артефактов. Команда запуска и уровни контроля описаны в [автоматизации AI-среды](../../../docs/harness/reference.md#автоматизация-ai-среды).
7. Коммит проходит git-хук с проверкой документации. Решение из чата записывает `/capture`, напоминание о неразобранных сессиях разбирает `/harvest`.
8. Этап закрывает `/stage`: показывает прогресс, проверяет готовность и ставит тег после подтверждения владельца.

## Какой скилл когда

| Ситуация | Скилл |
|---|---|
| впервые в репозитории, нужен обзор | `/harness-guide` |
| что дальше, как идет работа, завести задачу или баг | `/work` |
| разбить цель или MVP на фичи | `/epic-new` |
| взять готовую фичу в работу | `/work-start` |
| описать новую фичу, закрыть открытые вопросы | `/speckit-specify`, затем `/speckit-clarify` |
| план, задачи, проверка артефактов, чек-лист | `/speckit-plan`, `/speckit-tasks`, `/speckit-analyze`, `/speckit-checklist` |
| реализация, код разошелся с артефактами | `/speckit-implement`, `/speckit-converge` |
| фича может задеть чувствительный код | `/hot-zones`, хук вызывает его сам перед планом |
| архитектурное решение по элементу-исследованию | `/decide` |
| изменить принципы, стек или процесс | `/speckit-constitution`, затем `/audit` |
| в чате прозвучало решение или факт | `/capture` |
| пришло напоминание о неразобранных сессиях | `/harvest` |
| после правок документации или перед пилотной фичей | `/docs-sync`, `/cold-start` |
| после правки харнеса, смены модели или версии Claude Code | `/harness-eval` |
| этап завершен или нужно понять, на каком этапе проект | `/stage` |

## Что харнес делает сам

- При старте сессии включает git-хук, показывает нарушения согласованности и напоминает о неразобранных сессиях.
- Перед командой Bash просит подтверждение, если команда пишет в конституцию. После правки файла показывает замечания проверки документации по этому файлу. Раз в несколько ходов просит найти незаписанные решения.
- Перед коммитом проверяет шапки, ссылки, метки, карту владельцев, дрейф шаблонов Spec Kit, трекер, каталог кирпичиков и рост версии конституции.
- Выполняет недиалоговые шаги фичи: план, задачи, сверку артефактов, тест первым, реализацию, проверку завершения, синхронизацию документов. Цепочка `feature-chain` на автономном уровне идет без остановок, если план не задел горячие зоны.
- Выводит статусы фич и эпиков из артефактов, считает очередь по зависимостям, проверяет готовность этапа.
- Тесты харнеса и сценарии поведения запускаются командой и идут без участия человека, но CI их не гоняет.

## Где нужен владелец

- Описать MVP и разложить цель на фичи, перевести элемент трекера из "идея" в "готово к работе".
- Утвердить спецификацию и ответить на уточняющие вопросы.
- Сказать, затрагивает ли фича горячую зону: агенту запрещено решать это самому.
- Выбрать вариант архитектурного решения, без выбора владельца ADR не принимается.
- Подтвердить правку конституции, объявить конец переходного режима.
- Подтвердить запись знаний из чата, которую показал `/capture`.
- Провести ревью кода, у этого шага нет автономного уровня, и утвердить контрольные точки цепочки.
- Поставить тег этапа и решить, отправлять ли его в удаленный репозиторий.
- Запускать тесты харнеса и сценарии поведения руками, пока нет CI.

## Границы

- Файлы не правь, статус элементов не меняй, скиллы Spec Kit не запускай: только рассказывай и предлагай команду.
- Числа, этапы и прогресс бери командами из шага 2, а не из этого файла и не из памяти.
