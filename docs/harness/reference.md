# Справочник харнеса

> **Отвечает за:** как запускать скиллы, скрипты, тесты и сценарии, описание каждого скилла и скрипта, настройки хуков, формат сценариев поведения и типовые ситуации.
> **Не содержит:** возможностей ([capabilities.md](capabilities.md)), схемы зависимостей ([infrastructure.md](infrastructure.md)), гейтов ([quality-gates.md](quality-gates.md)) и шагов самих скиллов, они лежат в файлах `SKILL.md`.
> **Читать когда:** нужно запустить проверку, скилл или тест, настроить клон или разобраться с сообщением проверки.
> **Проверено при версии конституции:** 3.0.0

**TL;DR:** клон настраивается одной командой git, скиллы вызываются как `/имя`, проверки и тесты запускаются командами Python. Шаги скиллов описаны в их файлах, здесь только когда и как их вызывать. Что не определено, записано в [реестре отложенных решений](../decisions/README.md#отложенные-решения).

## Первичная настройка клона

После клонирования выполните один раз:

```bash
git config core.hooksPath .githooks
```

Затем перезапустите Claude Code, чтобы применились настройки проекта. В сессиях Claude Code git-хук включается автоматически при старте, если он выключен.

## Проверка документации

Запуск, нужны Python 3 со стандартной библиотекой, а также git, diff и patch:

```bash
python3 tools/docs-lint.py
```

Проверяются:

- шапка в каждом файле документации и инструкций, включая скиллы проекта
- относительные ссылки и якоря
- наличие каждого файла в [карте источников истины](../README.md#карта-источников-истины)
- ссылка на реестр отложенных решений там, где есть неопределенные темы
- запрещенные символы типографики
- формат версии и дат конституции
- переопределение шаблона задач, в котором тесты обязательны
- настройки плагинов проекта
- наличие каждого файла харнеса на [схеме связей](infrastructure.md#схема-связей) и в этом справочнике
- запись о тестах для каждого файла харнеса в `tests/harness/coverage.json`
- метка актуальности в шапке не старше минорной версии конституции
- цепочки подключения: импорт `AGENTS.md` в `CLAUDE.md`, скрипты хуков, команды хуков Spec Kit и скиллы, имена скиллов, строка `.omc/` в `.gitignore`
- существование принципов, на которые ссылаются тексты, и путей, упомянутых в документации
- совпадение переопределений шаблонов с ядром Spec Kit и с их патчами
- версия конституции в планах фич, когда они появятся
- наличие каждого ADR в указателе реестра решений
- трекер работы: корректность элементов и их связей, привязка каждой фичи в `specs/` к элементу трекера
- реестр горячих зон: категории и статусы, размеченные зоны с известной категорией и уровнем контроля, правило `ask` в настройках для каждого пути зоны
- каталог образцов: статусы, эталонный путь и существующий коммит проверки
- поля в артефактах фич: Control level в спецификации, Hot zones touched и Pattern в плане, значения из реестров, и наличие этих полей в переопределениях шаблонов
- воркфлоу проекта в `.specify/workflows`: шаги команд есть в каталоге кирпичиков и не диалоговые, после каждого шага команды идет проверка, скиллы и скрипты существуют, уровни контроля известны
- каталог кирпичиков воркфлоу: уникальные имена, существование скиллов исполнителей, допустимые уровни контроля, согласованность статуса с исполнителем, запрет автономного уровня для диалоговых шагов

Режимы запуска: `--staged` для git-хука, `--hook` для хука после правки, `--session` для хука старта сессии, `--stamp <файл>` для метки актуальности, `--update-patches` и `--rebuild-overrides` для переопределений шаблонов.

Запуск в CI сознательно отложен, см. [реестр отложенных решений](../decisions/README.md#отложенные-решения). Пока единственная защита это git-хук и хук старта сессии, поэтому согласованность `main` держится на дисциплине, а не на гарантии.

Режим `--staged` запускает git-хук. Он дополнительно проверяет по индексу, что версия конституции стала больше прежней и что в ней нет временного отчета о синхронизации. Остальные проверки читают рабочее дерево.

## Скиллы проекта

Скиллы вызываются командой вида `/имя` в сессии Claude Code. Шаги каждого скилла описаны в его файле, здесь указано только, когда его запускать.

| Скилл | Когда вызывать | Что делает | Файл |
|---|---|---|---|
| `capture` | в чате прозвучало решение или факт, которого нет в файлах | находит кандидатов, определяет владельца, показывает правку и записывает после подтверждения | `.claude/skills/capture/SKILL.md` |
| `harvest` | пришло напоминание о неразобранных сессиях | ищет повторяющиеся фразы, которых нет в документации, и показывает память Claude | `.claude/skills/harvest/SKILL.md` |
| `cold-start` | после правок документации и перед пилотной фичей | свежий агент отвечает на контрольные вопросы только по репозиторию, считается размер входного контекста | `.claude/skills/cold-start/SKILL.md` |
| `docs-sync` | запускает хук Spec Kit, можно вручную после правок | сверяет изменившиеся факты с владельцами, обновляет метки, запускает проверку | `.claude/skills/docs-sync/SKILL.md` |
| `audit` | после поправки конституции и перед пилотной фичей | отдельный агент ищет противоречия между конституцией и файлами харнеса | `.claude/skills/audit/SKILL.md` |
| `harness-eval` | после правки харнеса, после смены модели или версии Claude Code | прогон сценариев поведения на нескольких моделях и разбор провалов | `.claude/skills/harness-eval/SKILL.md` |
| `hot-zones` | запускает хук Spec Kit перед планом, можно вручную | спрашивает владельца о горячих зонах фичи и записывает ответ | `.claude/skills/hot-zones/SKILL.md` |
| `epic-new` | нужно разбить большую цель, например MVP, на фичи | в диалоге с владельцем создает эпик и список его фич в трекере, спецификации не создает | `.claude/skills/epic-new/SKILL.md` |
| `work-start` | пора взять следующую фичу из трекера в работу | проверяет готовность и зависимости, готовит вхождение для `/speckit-specify`, привязывает спецификацию к элементу | `.claude/skills/work-start/SKILL.md` |
| `work` | вопрос "что дальше", "как идет работа", нужно завести простой элемент | показывает доску и очередь, создает простые элементы, меняет статус по команде владельца | `.claude/skills/work/SKILL.md` |

## Скиллы Spec Kit

Их установила интеграция Spec Kit, они лежат в `.claude/skills/speckit-*` и вызываются как `/speckit-имя`.

| Скилл | Когда вызывать | Что делает |
|---|---|---|
| `speckit-constitution` | меняются принципы проекта | обновляет конституцию по шаблону, повышает версию, готовит временный отчет |
| `speckit-specify` | начинается новая фича | создает спецификацию из описания и каталог фичи |
| `speckit-clarify` | в спецификации есть открытые вопросы | задает до пяти вопросов, ответы записывает в спецификацию |
| `speckit-plan` | спецификация утверждена | составляет план, исследование, модель данных и контракты, проверяет по конституции |
| `speckit-tasks` | план готов | составляет упорядоченный список задач, тесты идут первыми |
| `speckit-analyze` | список задач готов, реализация не начата | проверяет согласованность спецификации, плана и задач, ничего не меняет |
| `speckit-checklist` | нужен чек-лист под фичу | создает чек-лист по запросу |
| `speckit-implement` | задачи утверждены | выполняет задачи из списка |
| `speckit-converge` | код расходится с артефактами | сверяет код с артефактами и дописывает недостающие задачи |

## Скрипты

Все скрипты написаны на Python 3 без сторонних пакетов.

| Скрипт | Назначение | Запуск |
|---|---|---|
| `tools/docs-lint.py` | проверка согласованности харнеса | `python3 tools/docs-lint.py` и режимы из раздела выше. Код возврата 0 если нарушений нет, 1 если есть, 2 при неверном вызове или блокирующем замечании хука после правки |
| `tools/guard-constitution.py` | запрос подтверждения при записи в конституцию | запускает хук PreToolUse, читает данные хука из stdin, при подозрительной команде печатает решение `ask` |
| `tools/capture-reminder.py` | напоминания о записи знаний | `stop`, `end`, `compact`, `start` запускают хуки, `clear` снимает напоминание вручную. Частота напоминания в ходах задается переменной `CAPTURE_REMIND_EVERY`, по умолчанию 12, ноль выключает. Код возврата: `stop` возвращает 2, когда пора напоминать, иначе 0, неверный вызов возвращает 1 |
| `tools/check-feature.py` | проверка артефактов фичи между шагами цепочки | `python3 tools/check-feature.py spec`, `plan`, `autonomy`, `tasks` или `done`. Каталог фичи берется из `.specify/feature.json`. Код возврата 0 если проверка пройдена, 1 если нарушение, 2 если нет каталога фичи или этап неизвестен |
| `tools/harvest.py` | поиск повторяющегося контекста | `python3 tools/harvest.py` с флагами `--min`, `--words`, `--limit`. Только читает и печатает |
| `tools/work.py` | трекер работы | `python3 tools/work.py board`, `next`, `show W003`, `new`, `link`, `set`, `check`, подробности в разделе о трекере. Код возврата 0 успех, 1 нарушения проверки, 2 неверный вызов |
| `tools/harness-eval.py` | сценарии поведения агента | `python3 tools/harness-eval.py` с флагами из раздела о тестах. Код возврата 0 если рабочая модель прошла все, 1 если есть провалы, 2 при ошибке запуска |

## Трекер работы

Трекер хранит эпики и элементы работы файлами в каталоге `work/`, это данные зоны продукта, инструмент относится к харнесу. Решение записано в [ADR 0009](../decisions/0009-file-work-tracker.md). Трекер владеет очередностью, зависимостями и приоритетами, а Spec Kit владеет спецификацией, планом и задачами фичи, единственная связь между ними поле `spec`.

Один элемент это один файл в каталоге `work/` с именем вида W001-имя.md: шапка между строками `---` из плоских строк `ключ: значение`, затем описание свободным текстом.

| Поле | Значение |
|---|---|
| `id` | номер вида W001, имя файла начинается с него |
| `title` | название |
| `type` | эпик, фича, баг, инцидент, исследование, задача, харнес |
| `parent` | номер эпика, связи только вверх |
| `depends` | список номеров вида `[W001, W002]` |
| `kind` | простой, исследовательский, фундамент, обязателен у фичи |
| `priority` | P1, P2 или P3 |
| `control` | уровень контроля по умолчанию из [bricks.md](bricks.md#уровни-контроля), обязателен у фичи |
| `spec` | путь к каталогу фичи в `specs/`, только у фичи |
| `status` | ручной статус: идея, готово к работе, в работе, заблокировано, готово, отменено |

Статус не хранится там, где его можно вывести. Фича со `spec` получает статус из каталога Spec Kit: есть `spec.md` значит спецификация, есть `plan.md` значит план, в `tasks.md` не отмечено ни одной задачи значит задачи, отмечена часть значит в работе с долей, отмечены все значит готово. У такой фичи вручную можно оставить только отменено или заблокировано. Статус эпика собирается из его элементов: готово, в работе или не начат с долей выполненных. Ручной статус нужен элементам без `spec`, и только владелец переводит элемент из "идея" в "готово к работе".

| Команда | Что делает |
|---|---|
| `board` | эпики с прогрессом и их элементы, затем элементы без эпика |
| `next` | элементы со статусом "готово к работе", у которых все зависимости выполнены, по приоритету |
| `show W003` | элемент с выведенным статусом |
| `new` | создает файл со следующим номером, параметры `--type`, `--title`, `--slug` обязательны, остальные `--parent`, `--depends`, `--kind`, `--priority`, `--control`, `--status`, `--body`, невалидный элемент не записывается |
| `link W003 specs/003-имя` | привязывает элемент-фичу к каталогу фичи и снимает ручной статус |
| `set W003 --status СТАТУС` | меняет ручной статус по правилам выше |
| `check` | проверяет трекер, ее же запускает `tools/docs-lint.py` и git-хук |

Проверка `check` ловит: повтор и неверный формат номера, неизвестные значения полей, отсутствие обязательных полей, несуществующих родителя, зависимость и каталог фичи, циклы зависимостей и родителей, один каталог фичи у двух элементов, ручной статус у фичи со `spec`, автономный уровень у исследовательской и фундаментной фичи, а в обратную сторону каталог в `specs/`, не привязанный ни к одному элементу.

Диалоговые скиллы поверх трекера: `epic-new` создает эпик и фичи, `work-start` передает одну фичу в Spec Kit, `work` отвечает на вопросы о ходе работы. Эпики и фичи создаются только с участием владельца, содержимое MVP трекер не содержит и ждет описания владельцем, см. [реестр отложенных решений](../decisions/README.md#отложенные-решения).

## Автоматизация AI-среды

| Механизм | Где настроен | Что делает |
|---|---|---|
| настройки Claude Code | `.claude/settings.json` | отключает перечисленные в файле плагины, запрещает чтение `.env` инструментом Read, force push и `--no-verify`, требует подтверждения правки конституции. Новый установленный плагин нужно добавить в список |
| хук после правки | `.claude/settings.json`, `tools/docs-lint.py` | проверка после правки файла, подробности в таблице хуков ниже |
| хук перед командой | `.claude/settings.json`, `tools/guard-constitution.py` | запрос подтверждения при записи в конституцию, эвристика по тексту команды, а не гарантия |
| хуки Spec Kit | `.specify/extensions.yml` | перед `/speckit-plan` запускают `/hot-zones`, после `/speckit-implement` и `/speckit-constitution` запускают `/docs-sync`, после поправки конституции дополнительно предлагают `/audit` |
| цепочка фичи без диалога | `.specify/workflows/feature-chain/workflow.yml` | запускается командой `specify workflow run feature-chain -i spec="описание" -i control="автономный"`, нужна утвержденная спецификация фичи и ее каталог в `.specify/feature.json`. Шаги: план, задачи, реализация, синхронизация документов, после каждого шага команды проверка результата. Уровень контроля задается входом control: автономный без остановок и только если в плане нет горячих зон, контрольная точка с остановками после плана, задач и результата, сопровождение в цепочке невозможно. Неинтерактивные шаги применяют правила разрешений проекта только в доверенной папке. Причины в [ADR 0007](../decisions/0007-spec-kit-workflow-engine.md) |
| скилл `docs-sync` | `.claude/skills/docs-sync/SKILL.md` | сверяет изменившиеся факты с файлами-владельцами и запускает проверку |
| git-хук | `.githooks/pre-commit` | запускает проверку перед коммитом |
| переопределения шаблонов Spec Kit | `.specify/templates/overrides/tasks-template.md`, `.specify/templates/overrides/tasks-template.patch`, `.specify/templates/overrides/plan-template.md`, `.specify/templates/overrides/plan-template.patch`, `.specify/templates/overrides/spec-template.md`, `.specify/templates/overrides/spec-template.patch` | шаблон задач делает тесты обязательными и первыми, как требует принцип VI, шаблон плана записывает версию конституции, затронутые горячие зоны и образец, шаблон спецификации уровень контроля. Патч фиксирует отличие от ядра, проверка ловит расхождение после обновления Spec Kit |
| проверка при старте сессии | `.claude/settings.json`, `tools/docs-lint.py` с флагом `--session` | включает git-хук и показывает нарушения согласованности, подробности в таблице хуков ниже |
| метки актуальности | шапка каждого файла, `tools/docs-lint.py` с флагом `--stamp` | файл со старой мажорной или минорной версией конституции считается устаревшим, пока его не сверят и не поставят метку |
| скилл `audit` | `.claude/skills/audit/SKILL.md` | отдельный агент ищет противоречия между конституцией и файлами харнеса, хук Spec Kit предлагает его после поправки конституции |
| напоминания о записи знаний | `.claude/settings.json`, `tools/capture-reminder.py` | хуки Stop, PreCompact, SessionEnd и SessionStart напоминают о записи знаний, события и частота в таблице хуков ниже. Хуки PreCompact и SessionEnd ничего не передают модели и только помечают сессию |
| скилл `capture` | `.claude/skills/capture/SKILL.md` | записывает решение из чата владельцу после подтверждения |
| скилл `harvest` | `.claude/skills/harvest/SKILL.md`, `tools/harvest.py` | ищет повторяющийся контекст в расшифровках сессий и в памяти Claude |
| скилл `cold-start` | `.claude/skills/cold-start/SKILL.md` | проверка с чистого листа по контрольным вопросам и замер размера контекста |
| тесты харнеса | `tests/harness/`, `tests/harness/coverage.json`, `tests/harness/manifest.json` | проверяют скрипты, проводку хуков, git-хук и сам `docs-lint`, правило покрытия требует тест для каждого файла харнеса, манифест фиксирует состав харнеса |
| сценарии поведения агента | `evals/cases/`, `tools/harness-eval.py` | запускают Claude Code без интерфейса в чистой копии репозитория на нескольких моделях и проверяют файлы, вызовы инструментов и ответ |
| скилл `hot-zones` | `.claude/skills/hot-zones/SKILL.md` | опрашивает владельца о горячих зонах фичи и записывает ответ в реестр, настройки и план, хук Spec Kit вызывает его перед `/speckit-plan` на каждой новой фиче |
| скилл `harness-eval` | `.claude/skills/harness-eval/SKILL.md` | ручной прогон сценариев и разбор провалов |

Заметки к таблице:

- Формат расшифровок сессий внутренний и может измениться. Если `tools/harvest.py` перестал находить реплики, он предупреждает об этом.
- Состояние напоминаний лежит вне репозитория: `~/.claude/projects/<проект>/capture/`.
- Снять напоминание о неразобранных сессиях можно командой `python3 tools/capture-reminder.py clear`. Число в напоминании считает пометки, а не сессии: одна сессия со сжатием и закрытием учитывается дважды.
- `tools/harvest.py` читает только папку этого проекта в `~/.claude/projects`, чужие проекты не затрагиваются. Папка выводится из абсолютного пути репозитория, поэтому сессии, запущенные из подпапки, копии репозитория по другому пути и git worktree скрипт не видит.
- Claude Code, насколько известно, по умолчанию удаляет старые расшифровки примерно через тридцать дней. Это не проверено по документации. Поэтому напоминание о неразобранной сессии не стоит оставлять без внимания дольше месяца.

## Настройки хуков Claude Code

Хуки подключены в `.claude/settings.json`, все команды обращаются к скриптам через переменную `CLAUDE_PROJECT_DIR`.

| Событие | Отбор | Команда | Эффект |
|---|---|---|---|
| PreToolUse | Bash | `tools/guard-constitution.py` | запрос подтверждения при записи в конституцию |
| PostToolUse | Edit и Write | `tools/docs-lint.py` с флагом `--hook` | замечание по правленому файлу, код возврата 2 показывает его агенту |
| Stop | все | `tools/capture-reminder.py stop` | раз в 12 ходов просьба проверить незаписанные решения |
| SessionStart | все | `tools/capture-reminder.py start` и `tools/docs-lint.py` с флагом `--session` | напоминание о пометках, включение git-хука, нарушения согласованности |
| SessionEnd | все | `tools/capture-reminder.py end` | пометка сессии, в которой было не меньше шести ходов |
| PreCompact | все | `tools/capture-reminder.py compact` | пометка сессии со сжатием контекста |

Дополнительно в настройках перечислены отключенные плагины пользователя и правила разрешений: чтение `.env`, force push и коммит с `--no-verify` запрещены, правка конституции требует подтверждения.

## Тесты харнеса

Быстрые тесты скриптов, хуков и проверки документации:

```bash
python3 -m unittest discover -s tests/harness
```

Нужен только Python 3. Тесты работают во временных копиях репозитория и не трогают настоящие файлы и домашнюю папку.

Сценарии поведения агента, нужен установленный `claude`, расходуют токены:

```bash
python3 tools/harness-eval.py --list
python3 tools/harness-eval.py
```

Первая модель в списке `--models` рабочая и определяет код возврата, остальные показывают запас прочности. Дополнительные флаги: `--runs`, `--case`, `--slow`, `--suite cold-start`, `--parallel` (по умолчанию 3), `--threshold` (доля пройденных запусков, по умолчанию 0.67), `--timeout` (секунд на запуск, по умолчанию 600). Раннер выставляет `CAPTURE_REMIND_EVERY=0` в запусках, а переменная `HARNESS_EVAL_CLAUDE` подменяет команду `claude`, это нужно тестам раннера. Тот же прогон с разбором результата выполняет `/harness-eval`. По умолчанию рабочая модель `sonnet`, слабая `haiku`, на один запуск действует предохранитель в один доллар, его меняет флаг `--budget`. Лимита по токенам у владельца проекта нет.

Как тесты следуют за харнесом:

- Правило покрытия: проверка документации требует запись в `tests/harness/coverage.json` для каждого файла харнеса.
- Эталонный манифест: после осознанной правки харнеса его обновляют командой `UPDATE_MANIFEST=1 python3 -m unittest discover -s tests/harness -p 'test_manifest.py'`.
- Порядок исправления ошибки харнеса и перепрогон сценариев заданы [разделом процесса конституции](../../.specify/memory/constitution.md#процесс-разработки-и-контроль-качества).
- Эталонные данные хуков лежат в `tests/harness/fixtures/hooks/`. Данные событий PreToolUse и PostToolUse захвачены в живой сессии, остальные восстановлены по документации.
- Сценарии запускаются вручную, в CI они пока не гоняются, см. [реестр отложенных решений](../decisions/README.md#отложенные-решения).

## Формат сценария поведения

Сценарий лежит в `evals/cases/<имя>/case.json`. Имя папки становится именем сценария.

| Поле | Смысл |
|---|---|
| `description` | что проверяет сценарий |
| `prompt` | запрос, который получает агент |
| `setup` | необязательные шаги подготовки копии: `replace` заменяет текст в файле, `write` создает файл, `bump_constitution` повышает версию конституции |
| `graders` | список проверок результата |
| `slow` | необязательный признак медленного сценария, он запускается только с флагом `--slow` или по имени |
| `runs` | необязательное число запусков, заменяет общее значение |

Типы проверок:

| Тип | Что проверяет |
|---|---|
| `file_unchanged` | файл не изменился |
| `file_exists` | файл существует |
| `no_changes_matching` | нет созданных, измененных и удаленных файлов под маской |
| `regex_in_result` | шаблон найден в ответе агента |
| `tool_used`, `tool_not_used` | инструмент вызван или не вызван, с отбором по тексту входных данных |
| `init_lacks` | в списке скиллов, плагинов или агентов из события инициализации нет элементов под шаблон |

Вопросы `cold-start` строятся автоматически из `.claude/skills/cold-start/questions.md`, допускается любой из путей в обратных кавычках в ячейке владельца.

## Что делать, если

| Ситуация | Действие |
|---|---|
| проверка сообщает, что метка файла устарела | прочитать файл, сверить с конституцией, поправить, поставить метку командой `--stamp` |
| проверка сообщает, что переопределение шаблона расходится | после обновления Spec Kit выполнить `--rebuild-overrides`, после осознанной правки файла выполнить `--update-patches` |
| добавлен новый скилл, скрипт или хук | показать его на схеме связей, описать в этом справочнике, добавить запись в `tests/harness/coverage.json`, написать тест, обновить манифест |
| хук не сработал | перезапустить Claude Code, выполнить `python3 tools/docs-lint.py`, он проверяет пути хуков, затем прогнать тесты проводки |
| пришло напоминание о неразобранной сессии | выполнить `/harvest` или снять напоминание командой `clear` |
| тесты харнеса упали после правки | прочитать, какой случай упал: падение мутационного случая значит, что проверка перестала ловить поломку |
| нужна новая проверка в `docs-lint` | написать функцию `check_...` и мутационный случай в `tests/harness/test_docs_lint.py`, контрольный тест не даст оставить проверку без случая |
| нужен новый сценарий поведения | создать папку в `evals/cases/` с файлом `case.json` и запустить сценарий на двух моделях |
