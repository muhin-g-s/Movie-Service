# Конституция Movie Service

> **Отвечает за:** фундаментальные принципы проекта, технологический стек Backend и обязательные ограничения.
> **Не содержит:** инструкций агентам ([AGENTS.md](../../AGENTS.md)), критериев ревью ([code-review.md](../../code-review.md)), устройства системы ([docs/architecture](../../docs/architecture/README.md)).
> **Читать когда:** начинаете любую работу, добавляете технологию или меняете правила.

**TL;DR:** девять принципов, фиксированный стек Backend и переходный режим на время настройки платформы. Менять файл можно только поправкой с повышением версии.

## Основные принципы

### I. Разработка от спецификации
Каждая работа ДОЛЖНА начинаться с утвержденной спецификации в `specs/`.
Спецификация ДОЛЖНА описывать поведение с точки зрения пользователя и
критерии приемки, не предписывая реализацию. Планы реализации ДОЛЖНЫ
соответствовать утвержденным спецификациям, а задачи ДОЛЖНЫ быть достаточно
небольшими и допускать независимую проверку. Работа, не покрытая
утвержденной спецификацией, НЕ ДОЛЖНА попадать в merge. Реализация НЕ ДОЛЖНА
выходить за рамки утвержденной спецификации без ее предварительного
обновления. Перед завершением задачи НЕОБХОДИМО проверить выполнение
критериев приемки. Архитектурные решения ДОЛЖНЫ документироваться. Исключения
задают раздел "Переходный режим" и список ниже:

- Исправление бага: отдельная спецификация не требуется. Ожидаемое поведение
  ДОЛЖНО быть уточнено записью в `spec.md` существующей фичи, первым ДОЛЖЕН
  быть написан падающий регрессионный тест, затем выполняется исправление.
- Рефакторинг без изменения поведения: новая спецификация не требуется.
  Поведение ДОЛЖНО быть защищено существующими тестами, которые проходят до и
  после изменения. Изменение поведения под видом рефакторинга НЕ ДОПУСКАЕТСЯ.
- Срочное исправление инцидента в проде: допускается сначала остановить
  ущерб без спецификации. В течение того же рабочего цикла ДОЛЖНЫ быть
  выполнены разбор причин, запись в спецификацию или в реестр отложенных
  решений, регрессионный тест и проверка, что подобная ошибка ловится.

Исключения не отменяют принципы II-IX: контракты, тесты и безопасность
действуют и в них.

Обоснование: сервис строится с нуля по Spec Kit; общая, проверяемая
спецификация является единственным долговечным источником намерения и
основой для всех последующих артефактов (план, задачи, тесты). Исключения
нужны там, где спецификация до работы не добавляет ценности (рефакторинг) или
где скорость важнее порядка (инцидент), но намерение все равно фиксируется.
Причины и рассмотренные варианты: [ADR 0008](../../docs/decisions/0008-principle-i-exceptions.md).

### II. Модульный монолит в монорепозитории
Проект ДОЛЖЕН использовать монорепозиторий. Backend ДОЛЖЕН следовать
архитектуре модульного монолита: каждый модуль ДОЛЖЕН иметь четкую зону
ответственности и границы, а архитектура модулей ДОЛЖНА позволять развивать
их независимо друг от друга. Frontend и Backend ДОЛЖНЫ быть логически
разделены. Backend ДОЛЖЕН быть единственным источником истины для общего
состояния воспроизведения.

Обоснование: модульный монолит дает границы и независимую эволюцию модулей
без операционной стоимости распределенной системы; единый источник истины
на сервере исключает расхождение состояния воспроизведения между клиентами.

### III. Сначала контракт
Контракты ДОЛЖНЫ размещаться в отдельном пакете монорепозитория и быть
языконезависимыми. Для их описания ДОЛЖНЫ использоваться:

- OpenAPI для REST API, с генерацией TypeScript-клиента;
- AsyncAPI для документирования событий реального времени и других
  асинхронных взаимодействий; события Socket.IO ДОЛЖНЫ описываться в
  терминах его нативной модели: имя события, пространство имен (namespace),
  комната (room), структура данных и acknowledgement, если он используется;
- JSON Schema для валидации отдельных структур данных там, где это
  полезно.

Контракт событий ДОЛЖЕН однозначно задавать, какое сообщение уходит под
каким именем события и в каком пространстве имен или комнате, чтобы
Frontend мог принимать его штатным клиентом Socket.IO без знания
внутренностей Backend. Контракт ДОЛЖЕН быть закоммичен до того, как от него
начнут зависеть клиенты или E2E-тесты. Контракт является источником истины для общих типов:
клиенты и типы для Go и TypeScript ДОЛЖНЫ генерироваться из контрактов, а не
дублироваться вручную, и сгенерированный код НЕ ДОЛЖЕН редактироваться
вручную. Контракты ДОЛЖНЫ версионироваться; ломающие изменения
опубликованного контракта ДОЛЖНЫ выходить в новой мажорной версии с
документированным планом миграции. Ответы ДОЛЖНЫ использовать единый формат
ошибок со стабильными кодами. Внутренняя структура пакета контрактов
определяется отдельно на этапе планирования.

Обоснование: стабильный контракт позволяет клиентам, тестам и документации
развиваться независимо от внутренностей Backend, делает обратную
совместимость проверяемой и исключает расхождение типов между Go и
TypeScript.

### IV. Простота и масштабируемость
Следует выбирать наиболее простое решение, удовлетворяющее текущим
требованиям, и избегать преждевременной оптимизации и избыточных
архитектурных абстракций. Микросервисы НЕ ДОЛЖНЫ внедряться без
подтвержденной необходимости. Redis и другие дополнительные
инфраструктурные компоненты НЕ ДОЛЖНЫ добавляться без конкретного сценария
использования. Усложнение инфраструктуры ДОЛЖНО быть обосновано измеримыми
требованиями и зафиксировано в разделе Complexity Tracking плана с
указанием решаемой проблемы и отвергнутого более простого варианта.

Обоснование: молодая кодовая база быстрее всего обрастает стоимостью через
ненужную структуру и инфраструктуру; небольшая поверхность сохраняет
читаемую связь между спецификацией и кодом.

### V. Качество кода
Код ДОЛЖЕН быть читаемым, поддерживаемым и единообразно структурированным.
Функции и модули ДОЛЖНЫ иметь одну основную зону ответственности.
Предпочтение СЛЕДУЕТ отдавать явным зависимостям и понятным границам
модулей. Следует избегать дублирования кода, ненужных абстракций и
универсальных утилит. Необходимо следовать общепринятым соглашениям
используемых языков и фреймворков. TypeScript ДОЛЖЕН использоваться со
строгой конфигурацией типизации; использование `any` НЕ ДОПУСКАЕТСЯ без
явного обоснования в коде.

Обоснование: единообразный и явный код дешевле проверять на соответствие
спецификации и безопаснее менять.

### VI. Сначала тесты (TDD, НЕ ПОДЛЕЖИТ ОБСУЖДЕНИЮ)
Backend ДОЛЖЕН разрабатываться по TDD. Тесты ДОЛЖНЫ быть написаны и
наблюдаемо падать по правильной причине до реализации, которая их проходит;
затем следуют минимальная реализация и рефакторинг (Red-Green-Refactor).
Каждая пользовательская история в спецификации ДОЛЖНА соответствовать
хотя бы одному автотесту. Контрактные тесты ДОЛЖНЫ существовать для каждого
публичного эндпоинта и каждого события Socket.IO; контрактные тесты событий
ДОЛЖНЫ использовать официальный клиент Socket.IO. Интеграционные тесты
ДОЛЖНЫ покрывать каждое взаимодействие с внешней системой (PostgreSQL,
сторонние провайдеры данных о фильмах). Исправление ошибки ДОЛЖНО начинаться
с падающего регрессионного теста. Важные пользовательские сценарии ДОЛЖНЫ
покрываться E2E-тестами, которые проверяют систему через ее внешние
интерфейсы и НЕ ДОЛЖНЫ зависеть от внутренней реализации Backend. Все тесты
ДОЛЖНЫ проходить успешно перед завершением изменений; изменение с падающими
или пропущенными тестами НЕ ДОЛЖНО попадать в merge. Правила тестирования
Frontend определяются вместе с его технологическим стеком.

Обоснование: тесты, написанные первыми, превращают спецификацию в
исполняемые критерии приемки и не дают реализации незаметно подменить цель.

### VII. Безопасность
Секреты и учетные данные НЕ ДОЛЖНЫ попадать в репозиторий; конфигурация
ДОЛЖНА приходить из переменных окружения, которые ДОЛЖНЫ проходить проверку
и валидацию при старте. Все внешние входные данные ДОЛЖНЫ валидироваться
на Backend. Аутентификация и авторизация ДОЛЖНЫ обеспечиваться на стороне
сервера; пользователи ДОЛЖНЫ иметь доступ только к тем ресурсам, на
которые у них есть соответствующие права. Конфиденциальная информация НЕ
ДОЛЖНА попадать в API-ответы или логи.

Обоснование: Backend является единственной доверенной границей системы, и
только на ней проверки нельзя обойти.

### VIII. Наблюдаемость и эксплуатируемость
Backend ДОЛЖЕН писать структурированные (JSON) логи с request/correlation ID
на каждый запрос и ДОЛЖЕН предоставлять эндпоинты health и readiness.
Ошибки ДОЛЖНЫ логироваться с контекстом, достаточным для воспроизведения,
без секретов и персональных данных. Ключевые операции (задержка запросов,
доля ошибок, вызовы внешних провайдеров) ДОЛЖНЫ быть измеримы через метрики,
отдаваемые самим сервисом без дополнительных инфраструктурных компонентов.

Обоснование: сервис, который нельзя наблюдать, нельзя проверить в проде, а
критерии приемки из спецификации должны оставаться проверяемыми после
деплоя.

### IX. AI-нативная документация и среда
Документация пишется в первую очередь для человека и ДОЛЖНА быть понятна
ИИ-агенту. Для этого:

- У каждого факта ДОЛЖЕН быть ровно один файл-источник истины. Остальные
  места ДОЛЖНЫ ссылаться на него и НЕ ДОЛЖНЫ копировать содержимое. Карта
  источников истины ведется в
  [docs/README.md](../../docs/README.md#карта-источников-истины).
- Каждый файл документации и инструкций ДОЛЖЕН начинаться с шапки: за что
  отвечает, чего не содержит, когда читать.
- При изменении факта файл-источник ДОЛЖЕН быть обновлен в той же задаче.
  Ссылки между файлами ДОЛЖНЫ быть относительными и проверяемыми.
- Решение, которое сознательно не принято, ДОЛЖНО быть внесено в
  [реестр отложенных решений](../../docs/decisions/README.md#отложенные-решения),
  а в файлах-владельцах тема ДОЛЖНА быть помечена как не определенная.
  Агент НЕ ДОЛЖЕН придумывать содержимое для такой темы.
- Рабочее состояние и память агентов (`.omc/`, память Claude) эфемерны и НЕ
  являются источником истины. Каталог `.omc/` НЕ ДОЛЖЕН попадать в репозиторий.
- Разрешенные AI-зависимости проекта: Spec Kit, OMC и правила из этого
  репозитория. Плагины, которые пользователь установил на свой компьютер,
  кроме OMC, НЕ ДОЛЖНЫ использоваться без поправки конституции. Скиллы и
  коннекторы, которые предоставляет сама платформа Claude, правилом не
  затрагиваются.

Обоснование: агент читает только то, на что указывает ссылка, и принимает
прочитанное за истину; дубли расходятся, а выдуманное содержимое
превращается в ложные требования.

## Технологический стек

Основной стек Backend:

- Язык программирования: Go.
- База данных: PostgreSQL.
- Обмен данными в реальном времени: Socket.IO как основной протокол.

Контракты (см. принцип III):

- REST API: OpenAPI.
- События и асинхронные взаимодействия: AsyncAPI.
- Отдельные структуры данных: JSON Schema.

Инструменты тестирования:

- E2E-тестирование: Playwright.
- Язык E2E-тестов: TypeScript.

Правила:

- Backend ДОЛЖЕН разрабатываться на Go. TypeScript НЕ ДОЛЖЕН использоваться
  для реализации Backend.
- Socket.IO ДОЛЖЕН быть основным протоколом обмена данными в реальном
  времени. Чистые WebSocket без протокола Socket.IO НЕ ДОЛЖНЫ
  использоваться для событий приложения. Frontend ДОЛЖЕН принимать события
  через клиент Socket.IO, а Backend ДОЛЖЕН отправлять события по нативному
  контракту Socket.IO (именованные события, пространства имен, комнаты,
  acknowledgements), а не по самодельному протоколу поверх WebSocket.
- Серверная библиотека Socket.IO для Go ДОЛЖНА быть выбрана в плане первой
  фичи с событиями реального времени, и ее совместимость с официальным
  клиентом Socket.IO ДОЛЖНА быть подтверждена автоматическим тестом.
- Frontend НЕ входит в текущий этап разработки; его стек будет определен
  отдельно на последующих этапах поправкой к этой конституции.
- Технологии НЕ ДОЛЖНЫ заменяться без архитектурного обоснования,
  зафиксированного поправкой к этой конституции.
- Технология, не перечисленная в этом разделе, не выбрана. Агент НЕ ДОЛЖЕН
  выбирать ее самостоятельно (принцип IX).
- Добавление новых зависимостей ДОЛЖНО быть обосновано реальными
  требованиями проекта; зависимости ДОЛЖНЫ быть зафиксированы по версиям.
  Следует отдавать предпочтение проверенным решениям вместо собственных
  реализаций.
- Хранимые данные ДОЛЖНЫ иметь явную схему PostgreSQL с миграциями под
  контролем версий.

## Процесс разработки и контроль качества

- Работа идет по последовательности Spec Kit: `/speckit-specify`, затем
  `/speckit-clarify` (когда в спецификации есть открытые вопросы), затем
  `/speckit-plan`, `/speckit-tasks` и `/speckit-implement`. Пропуск шага
  ДОЛЖЕН быть явно указан в плане.
- Каждый план ДОЛЖЕН пройти Constitution Check до фазы 0 (исследование) и
  повторно после фазы 1 (проектирование); нарушения ДОЛЖНЫ быть устранены
  или обоснованы в Complexity Tracking.
- Каждый merge request ДОЛЖЕН ссылаться на реализуемую спецификацию и
  проходить проверку по критериям из [code-review.md](../../code-review.md).
  Процедура ревью и обязательные проверки CI сознательно не определены и
  внесены в
  [реестр отложенных решений](../../docs/decisions/README.md#отложенные-решения).
- Задачи в `tasks.md` ДОЛЖНЫ выполняться в порядке зависимостей; задача
  считается завершенной, только когда тест, написанный первым, проходит,
  критерии приемки проверены и чекбокс отмечен.
- Ошибка харнеса (скрипта, хука, проверки, скилла) ДОЛЖНА сначала стать тестом
  или сценарием поведения агента и только потом исправляться. Сценарии
  поведения агента ДОЛЖНЫ перепрогоняться при смене модели или версии Claude
  Code.
- Работа ведется на трех уровнях контроля шага: автономный, контрольная точка
  и сопровождение. Определение уровней находится в
  [bricks.md](../../docs/harness/bricks.md#уровни-контроля) и здесь не
  повторяется. Уровень по умолчанию ДОЛЖЕН быть записан в спецификации фичи.
- Горячие зоны из реестра
  [hot-zones.md](../../docs/architecture/hot-zones.md) поднимают уровень
  контроля. Агент НЕ ДОЛЖЕН сам решать, является ли затронутый код горячей
  зоной: он ДОЛЖЕН спросить владельца и записать ответ в реестр. Автономные
  режимы агента НЕ ДОЛЖНЫ запускаться на задачах в горячих зонах.
- Документация, спецификации, планы, задачи и прочие артефакты Spec Kit
  ДОЛЖНЫ быть написаны на русском. Идентификаторы кода, имена файлов и
  сообщения коммитов ДОЛЖНЫ быть написаны на английском. Заголовки шаблонов
  Spec Kit НЕ ДОЛЖНЫ переводиться: на них опираются команды Spec Kit.

## Переходный режим

Пока владелец проекта явно не объявил о переходе, действует переходный
режим:

- прямые коммиты в `main` допускаются, merge request не требуются;
- работа над AI-платформой и документацией ведется без спецификации;
- структура ведения git не определена.

Принципы II-IX действуют и в переходном режиме, в том числе для прямых
коммитов. Ревью поправок и merge request в переходном режиме заменяются
подтверждением владельца проекта.

Переходный режим заканчивается явным объявлением владельца проекта.
Объявление ДОЛЖНО быть оформлено поправкой конституции, которая удаляет этот
раздел. С этого момента все изменения идут через merge request и по
принципу I. Ожидается, что переход будет объявлен до начала реализации
первой фичи. Агент НЕ ДОЛЖЕН объявлять переход самостоятельно.

## Управление

Эта конституция имеет приоритет над всеми остальными практиками разработки
в репозитории и над противоречащими ей предпочтениями при реализации. Если
шаблон, скилл или соглашение противоречит ей, действует конституция, а
противоречащий артефакт ДОЛЖЕН быть обновлен.

Поправки ДОЛЖНЫ вноситься через `/speckit-constitution`, ДОЛЖНЫ
сопровождаться обоснованием и отчетом Sync Impact Report, ДОЛЖНЫ повышать
версию по правилам семантического версионирования (MAJOR при удалении,
переопределении или ослаблении принципов, MINOR при добавлении принципов
или существенном расширении правил, PATCH при уточнениях) и ДОЛЖНЫ
проходить ревью перед merge. Принцип с пометкой "НЕ ПОДЛЕЖИТ ОБСУЖДЕНИЮ"
может быть ослаблен только поправкой с повышением MAJOR-версии.
Конституция ДОЛЖНА пересматриваться при существенном изменении
архитектурных решений, в том числе при определении стека Frontend.
Изменение файла конституции без повышения версии НЕ ДОПУСКАЕТСЯ и отклоняется
проверкой документации. Правка файла агентом ТРЕБУЕТ подтверждения
пользователя.

Соответствие проверяется на каждом Constitution Check плана и при ревью по
[code-review.md](../../code-review.md). Инструкции для агентов находятся в
[AGENTS.md](../../AGENTS.md).
