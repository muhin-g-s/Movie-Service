# Code Review Guidelines

> **Отвечает за:** правила проверки кода: критерии, формат замечаний, приоритеты, итоговый отчет.
> **Не содержит:** определений принципов (они в [конституции](.specify/memory/constitution.md), пункты чек-листа лишь указывают, что проверить, и ссылаются на номер принципа), процедуры ревью и настроек CI.
> **Читать когда:** проверяете чужое изменение или завершаете свое.

**TL;DR:** изменение принимается, если нет замечаний P0 и P1. Нарушение принципа конституции с пометкой НЕ ПОДЛЕЖИТ ОБСУЖДЕНИЮ приравнивается к P1.

## 1. Цель Code Review

Цель Code Review - убедиться, что реализация:

- Соответствует требованиям и спецификации.
- Не нарушает согласованные архитектурные решения.
- Не содержит критических ошибок и потенциальных регрессий.
- Безопасна и надежна.
- Остается понятной и поддерживаемой.

Code Review не должен превращаться в поиск стилистических придирок или навязывание личных предпочтений.

## 2. Источники истины

При проверке использовать следующие источники:

1. [Конституция](.specify/memory/constitution.md) - фундаментальные принципы проекта. Ниже на них ссылки по номерам.
2. `spec.md` - функциональные требования.
3. `plan.md` - согласованные технические решения.
4. `tasks.md` - ожидаемый объем реализации.
5. [Архитектура](docs/architecture/README.md) - текущее устройство системы, когда оно определено.
6. Локальные соглашения и существующие паттерны кодовой базы.

Если реализация противоречит требованиям или архитектурному плану, необходимо указать на это.

Не считать личные предпочтения ревьюера основанием для обязательных изменений.

## 3. Критерии проверки

### 3.1. Корректность реализации

Проверить:

- Соответствие поведения системы требованиям.
- Корректность бизнес-логики.
- Обработку граничных случаев.
- Корректность работы с пустыми и некорректными данными.
- Отсутствие очевидных логических ошибок.
- Корректность взаимодействия компонентов.

### 3.2. Архитектура

Проверить:

- Соответствие согласованной архитектуре и границам модулей (принцип II).
- Состояние воспроизведения определяется только Backend (принцип II).
- Контракт обновлен и закоммичен раньше зависимого кода, типы сгенерированы, а не написаны руками (принцип III).
- Соблюдение границ ответственности модулей.
- Отсутствие циклических зависимостей.
- Отсутствие неоправданной связанности компонентов.
- Отсутствие дублирования бизнес-логики.
- Обоснованность новых абстракций.
- Отсутствие неоправданного усложнения существующей архитектуры и лишней инфраструктуры (принцип IV).

Не требовать применения архитектурных паттернов, если они не решают конкретную проблему.

### 3.3. Безопасность

Принцип VII. Проверить:

- Корректность аутентификации и авторизации.
- Проверку прав доступа на серверной стороне.
- Валидацию входных данных.
- Отсутствие утечек секретов и конфиденциальной информации.
- Безопасную обработку пользовательского ввода.
- Защиту от распространенных уязвимостей.
- Корректную обработку ошибок без раскрытия внутренних деталей системы.

### 3.4. Надежность

Проверить:

- Обработку ошибок и исключительных ситуаций.
- Корректность управления ресурсами.
- Отсутствие потенциальных утечек памяти и ресурсов.
- Корректность работы при конкурентном выполнении операций.
- Отсутствие очевидных race conditions.
- Корректность транзакций и целостность данных.
- Предсказуемое поведение при недоступности внешних зависимостей.

### 3.5. Производительность

Проверить:

- Отсутствие очевидных алгоритмических проблем.
- Отсутствие лишних запросов к базе данных.
- Отсутствие N+1 запросов.
- Корректность использования индексов там, где они необходимы.
- Отсутствие ненужных вычислений и операций ввода-вывода.
- Обоснованность использования кеширования.

Не требовать преждевременной оптимизации без подтвержденной проблемы.

### 3.6. Тестирование

Принцип VI. Проверить:

- Тест написан до реализации и падал по правильной причине (TDD).
- Контрактные тесты есть для каждого публичного эндпоинта и события Socket.IO.
- Интеграционные тесты есть для каждого взаимодействия с внешней системой.
- Нет пропущенных и падающих тестов.

- Наличие тестов для новой функциональности.
- Покрытие основных сценариев использования.
- Проверку граничных случаев.
- Проверку обработки ошибок.
- Наличие регрессионных тестов для исправленных ошибок.
- Соответствие тестов фактическим требованиям.

Не считать наличие тестов гарантией корректности реализации.

### 3.7. Поддерживаемость

Проверить:

- Читаемость и понятность кода.
- Понятность именования.
- Отсутствие ненужного дублирования.
- Отсутствие мертвого кода.
- Отсутствие неиспользуемых зависимостей.
- Обоснованность комментариев.
- Соответствие существующим соглашениям проекта.

Не предлагать рефакторинг кода, не относящегося к проверяемым изменениям, без веской причины.

### 3.8. Наблюдаемость

Принцип VIII. Проверить:

- Логи структурированы и содержат correlation ID.
- Ошибки логируются с контекстом, без секретов и персональных данных.
- Ключевые операции измеримы метриками.

### 3.9. Документация

Принцип IX. Проверить:

- Изменившийся факт обновлен в файле-владельце, дублей нет.
- Ссылки между файлами относительные и работают.
- Для отложенных тем нет выдуманного содержимого.

## 4. Формат замечаний

Каждое замечание должно содержать:

1. **Проблему** - что именно неправильно.
2. **Расположение** - файл и конкретная строка или диапазон строк.
3. **Последствия** - к чему может привести проблема.
4. **Рекомендацию** - как ее исправить.

Замечания должны быть конкретными, воспроизводимыми и технически обоснованными.

Не создавать замечания на основании предположений, если их нельзя обосновать.

## 5. Приоритеты замечаний

Использовать следующую классификацию:

| Приоритет | Значение |
|---|---|
| P0 - Critical | Критическая уязвимость, потеря данных или поломка системы |
| P1 - High | Существенная ошибка, серьезная регрессия или нарушение ключевого сценария |
| P2 - Medium | Ошибка, затрагивающая отдельную функциональность или важный граничный случай |
| P3 - Low | Незначительная проблема, не влияющая существенно на работу системы |

Не завышать приоритет замечаний.

P0 и P1 требуют исправления до принятия изменений. Нарушение принципа с пометкой НЕ ПОДЛЕЖИТ ОБСУЖДЕНИЮ приравнивается к P1.

P2 и P3 должны быть явно зафиксированы, но необходимость исправления определяется с учетом контекста.

## 6. Ограничения ревьюера

Ревьюер не должен:

- Изменять код самостоятельно без соответствующего поручения.
- Переписывать реализацию ради личных предпочтений.
- Предлагать необоснованный рефакторинг.
- Дублировать уже существующие замечания.
- Считать отсутствие идеального решения ошибкой.
- Требовать изменений, не связанных с требованиями или качеством реализации.
- Утверждать, что проверки прошли, если они фактически не выполнялись.

Если для проверки недостаточно контекста, необходимо запросить дополнительные сведения.

## 7. Итоговый отчет

По завершении Code Review сформировать отчет следующего вида:

### Общая оценка

Краткое описание качества реализации и соответствия требованиям.

### Найденные проблемы

Для каждой проблемы указать:

- Приоритет.
- Файл и строки.
- Описание проблемы.
- Возможные последствия.
- Рекомендацию по исправлению.

Если проблем не обнаружено, явно указать это.

### Проверки

Перечислить выполненные проверки:

- Анализ изменений.
- Запуск тестов.
- Статический анализ.
- Проверка соответствия спецификации.

Указывать только фактически выполненные проверки.

### Результат

Один из трех статусов:

- **Approved** - критических и существенных замечаний нет.
- **Approved with comments** - есть некритичные замечания, не блокирующие принятие изменений.
- **Changes requested** - обнаружены проблемы, требующие исправления до принятия изменений.

## 8. Основной принцип

Code Review должен повышать качество проекта, а не увеличивать сложность разработки.

Приоритеты:

1. Корректность.
2. Безопасность.
3. Надежность.
4. Соответствие архитектуре.
5. Поддерживаемость.
6. Производительность.

Предпочитать минимальные обоснованные изменения масштабным переделкам.

## 9. Не определено

Кто ревьюит, обязательные проверки CI и особенности проверки продуктовых сценариев пока не определены. Решим, когда придет время, см. [реестр отложенных решений](docs/decisions/README.md#отложенные-решения).
